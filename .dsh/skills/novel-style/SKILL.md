# novel-style

你管**怎么写**，不管**写了什么**（那是 `novel-consistency`）。

文风档案存在 **`novel/project.json` → `settings.style`**。选这里是因为 GUI 从不写 `project.json`（只读），所以档案不会被界面覆盖;而 `settings` 已经是项目级配置的既定位置(`wordCountGoal` 就在那里)。**GUI 没有它的编辑器——档案只由你维护。**

## 铁律：模板是形状，不是内容

下面的模板给出**字段名**。**没有一个值是默认可填的。**

**任何一句你没有在正文里找到证据、作者也没有明说的规则，都不要写。** `banned` 可以是空的，`dialogue` 可以整项省略——**空档案是诚实的，编出来的档案会让 `novel-writer` 照着一条假规则写下去。**

特别是：**不要照抄模板里的示例值。** 它们只是占位。

## 档案格式

```json
{
  "settings": {
    "style": {
      "status": "proposed",
      "basis": "从 1 章草稿（约 1900 字）归纳",
      "pov": "……",
      "tense": "……",
      "tone": "……",
      "distance": "……",
      "sentence": "……",
      "paragraph": "……",
      "diction": ["……"],
      "banned": ["……"],
      "dialogue": "……",
      "sample": "……"
    }
  }
}
```

- `status`: **`proposed`**（你归纳的，作者还没看过）或 **`confirmed`**（作者明确认可过）。**没有作者确认就只能是 `proposed`。**
- `basis`: 一句话说明你从多少文本里归纳的。**证据越薄，这条越重要**——它让作者知道自己该审多仔细。
- 其余字段**都可选**。写了就要遵守；不确定就省略，不要写"待定"。
- `sample`: 一段作者认可的正文，比任何形容词都准。**从正文里摘，不要自己写。**

## 先确认，不能确认就标记

优先用 `ask_user_question` 把归纳结果交给作者确认，得到认可才写 `status: "confirmed"`。

**若你无法与作者交互**（被委派、自动运行、没有提问通道）：**照常写入，但必须是 `status: "proposed"`，并在最终报告里明说"未经作者确认"。** 不要因为问不到人就不写，也不要假装确认过。

## 从既有正文归纳

1. 选样本：**`status: final` 或 `revised` 的章节优先**。
2. **若一章定稿都没有**（新项目常见）：用现有的草稿，但按下面的"证据不足"处理，**不要停下来问**。
3. 从样本里归纳**实际存在**的视角、时态、句长分布、段落长度、用词倾向、对白格式。
4. 写完 `status` 与 `basis`，然后在报告里请作者确认。

### 证据不足时

- **少于两章、或总量太薄**时，一个样本分不清"作者的习惯"和"这一章的偶然选择"。**明说这一点**，并把 `basis` 写清楚（几章、多少字）。
- 宁可**少写几条**，也不要为了填满模板而写。字段少但每条有据，比字段齐但一半是猜的有用得多。
- **没有对白就省略 `dialogue`**；没有回避用词就让 `banned` 为空数组。

## `banned` 的两个来源，不要混

| 来源 | 能写吗 |
|---|---|
| **作者明说的**禁用词 | 能，照抄作者的原话 |
| **你在正文里数出来的**口头禅（同一个词反复出现，你能指出在哪几处） | 能，但要能**指出证据** |
| **通用的套路化表达**（"不禁"、"不由得"……） | **不能。** 这不是作者的偏好，是你的偏好。写进去等于替作者定文风 |

**空 `banned` 是完全合格的结果**。在薄样本上编出一串"禁用词"，是这份档案最容易犯、也最误导人的错误。

## 三种用法

| 场景 | 做法 |
|---|---|
| **写作前** | 读档案，当作硬约束交给 `novel-writer` |
| **润色某章** | 逐条核对，只改违反档案的地方，**保留作者的原意与情节** |
| **统一全书** | 抽样各章，报告偏离处 + 具体改法；改动量大时**先给清单让作者选**，不要一次重写多章 |

## 与 GUI 生成的关系

GUI 的「随机生成」有一套**每次调用**的风格预设（简练/详实/古雅/平实/诡谲），那是**单次生成的临时方向**，与本书文风档案是两回事。两者冲突时**档案优先**。

## 写回 `project.json` 的规矩

整个文件是**整体覆写**的，漏掉字段就是删掉它们。所以：

- **先读、再改、整份写回**，保留 `schemaVersion`/`id`/`title`/`author`/`createdAt`/`updatedAt`/`defaultTimelineId`/`settings.wordCountGoal` 等一切既有字段。
- **不要动 `updatedAt`**：它是"小说内容被改动"的时间戳，写一份档案不是内容改动。（界面也不为读取动它。）
- 只增改 `settings.style` 这一个键。

## 检查清单

只在**有证据**的维度上检查；没有对应正文的条目跳过，不要硬判。

- **视角与人称**：一章之内不切换；不越界进入非视角人物的内心。
- **时态**：不在一段里来回跳。
- **句长节奏**：连续长句拖垮节奏，连续短句显得急促。按档案的比例来。
- **段落**：对白是否独立成段；有没有整页单段。
- **用词**：档案里的 `banned` 一个都不该出现；套路化表达要数着用。
- **对白**：引号样式是否统一；每个人说话的方式能否区分——**若去掉提示语就分不清谁在说，那是问题**。（正文里没有对白时，这一条不适用。）
- **信息密度**：不要在文风检查里改情节。只改"怎么说"。

## 报告方式

- 引用原句 → 指出违反了档案的哪一条 → 给出改法。**一次只改这一处。**
- 不要把你的偏好当成规则。档案里没写的，你只能**建议**，不能当成违反。
- 作者明确说"这里我就要这么写"时，**改档案**，不是改正文。
- 报告里必须包含：档案的 `status`、`basis`、以及**你不确定的那几条**（尤其是证据薄的维度）。
