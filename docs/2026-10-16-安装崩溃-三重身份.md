# 插件安装导致 web-boot 崩溃 —— 根因与解决方案

- 崩溃日志：`crash-2026-10-16T12-47-37-588Z-web-boot.log`（本地 20:47:37，另有 20:47:03、20:47:26 两次）
- 触发动作：20:46:44–20:47:01 通过插件管理器（dshmarket）安装 `dsh-context` / 更新 `dsh-cost-meter`
- 结论：**这是一次新的、与 18:54 那次完全不同性质的故障**。不是旧核心包遮蔽运行时，而是**插件改名后客户端 bundle 的自注册 id 与包名不一致**，违反了客户端的注册契约。

---

## 一、先排除旧病：不是"旧包顶掉运行时"

| 检查项 | 结果 |
|---|---|
| `profiles\desktop\node_modules\@deepseek-ai` | **目录不存在**（没有任何被提升上来的核心包） |
| 顶层依赖 | 只有 `dsh-context` / `dsh-cost-meter` / `dshmarket` 三个软链，指向 `.pnpm/<pkg>@<ver>` |
| `pnpm-workspace.yaml` | `nodeLinker: hoisted` 已被删除（文件里留着"别再放回来"的注释） |
| 崩溃日志类型 | `source: web-boot`（渲染进程启动审计），**不是** `host` 崩溃；19:21 之后再无 host 崩溃 |

所以旧方案（isolated linker + 不进 `dependencies`）是有效的，**不要回退**。

---

## 二、根因：`dsh-novel` 这个 id 与包名 `dsh-novelsupport` 不一致

### 2.1 两条日志说的其实是同一件事

```
host:      Error: web boot: 1 entry did not activate
           dsh-novelsupport: import failed (see console for the import error)

renderer:  Uncaught Error: client-modules: duplicate factory registration for "dsh-novel"
           (bundle executed twice without invalidate?)
```

- 第一条：启动审计发现有一行**没激活**，且行名是 **`dsh-novelsupport`**（= 包名，即 patch 里 insert 的 `name`）。
- 第二条：模块系统拒绝了一个**重复注册**，重复的 id 是 **`dsh-novel`**（= bundle 自己声明的 id）。

这不是两个 bug，而是**同一个身份错位的两种表现**。

### 2.2 客户端有硬性契约（已从 `app.asar` 源码逐条核对）

注册契约在 `@deepseek-ai/dsh-client-modules/lib/client.js`：

| 位置 | 代码 | 含义 |
|---|---|---|
| 第 569-576 行 | `register()`：`if (this.bootstrapIds.has(id) \|\| this.factories.has(id)) throw ... duplicate factory registration for "${registrationName}"` | 同一个 id **只能注册一次** |
| 第 610-640 行 | `arrive(row)`：执行完 bundle 后 `if (this.factories.has(id)) return "registered"`，否则记 `loaded without registering "${id}" via __ModuleLoader__.load`，最终 `throw could not load "${id}"` | **bundle 必须用"行自己的 id"注册**，用别的 id 注册等于没注册 |
| 第 630-637 行 | `executedBundleUrls` / `failedBundleUrls` | 同一个 URL 不会重放（注释明说"a replay would stop again at the first duplicate registration"） |

而"行自己的 id"是怎么来的？在 `lib/index.js`：

| 位置 | 代码 | 含义 |
|---|---|---|
| 第 649-653 行 | `compose()` → `entries` → `this.table.get(entry.id)` | **图的每一行 = 一个包名**（`graphRow(packageName, rev, ...)`） |
| 第 871-886 行 | `reconcilePackage(packageName)`：`this.table.set(packageName, ...)` | 客户端模块表**以包名为键** |

也就是说：**行 id = 包名 = `dsh-novelsupport`**，而你的 bundle 里写的是 `id: 'dsh-novel'`。

### 2.3 于是必然发生下面这条链

1. 某一行（combo 批处理）执行到 novel 的客户端脚本 → 它注册成 `dsh-novel`。此时表里没有 `dsh-novel`，注册成功；但**行 `dsh-novelsupport` 仍然没有工厂**。
2. 轮到 `dsh-novelsupport` 这一行自己的传输（或它的回退 URL）→ 脚本**再执行一次** → `register()` 命中第 573 行的守卫 → 抛 `duplicate factory registration for "dsh-novel"`。
   - 日志里紧接着的 `loaded without registering "dsh-novelsupport"` / `could not load "dsh-novelsupport"` 是同一行的后续，未必要等到报出来窗口就已经被判失败。
3. 该行永远无法 materialize → 宿主侧那一行 `import failed` → 渲染进程审计抛 `web boot: 1 entry did not activate` → `reportFatal(..., "web-boot")` 写崩溃日志。

### 2.4 仓库里能找到的证据

改名提交 `5b2f832 "chore: 包名改为 dsh-novelsupport"` **只改了三个文件**：`package.json`、`cordis.patch.yml`、`tools/impl-selftest.mjs`。

而 bundle 的 id 是**构建期硬编码**的：

```js
// tools/build-client.mjs:27
const PACKAGE_ID = 'dsh-novel'
// :62  id: '${PACKAGE_ID}'   → 生成 client/client.js:13  id: 'dsh-novel'
```

自测还把旧 id 当成契约锁死了：

- `tools/client-selftest.mjs:112` — `assert(entry.id === 'dsh-novel', ...)`
- `tools/impl-selftest.mjs:1392` — `assert(inserted.id === 'dsh-novel', 'the plugin id stays dsh-novel — it is the route prefix and the skill namespace')`

**关键区分**：`inserted.id`（插件身份，路由前缀 `/dsh-novel`、写头 `x-dsh-novel`、localStorage 键、技能命名空间）留在 `dsh-novel` 是**对的、必须保留**；但 **`entry.id`（客户端模块 id）不该跟它绑在一起** —— 它必须等于包名，否则上面 2.2 的契约一定被违反。

## 三、解决方案

### 3.1 改一处：让 bundle 的注册 id 等于包名（保留一切对外的"身份"）

**`tools/build-client.mjs`** —— 把硬编码换成"从 package.json 读包名，允许显式覆盖"：

```js
// 顶部
import { readdirSync, readFileSync, writeFileSync } from 'node:fs'
import { createRequire } from 'node:module'      // 新增

// 第 27 行：删掉 const PACKAGE_ID = 'dsh-novel'
// 换成：
/**
 * The client module id MUST equal the package name: the host composes one graph row
 * per package (dsh-client-modules/lib/index.js `graphRow(packageName, ...)`), and the
 * loader verifies the row's own id registered. A bundle that registers under any other
 * id both fails its own row ("loaded without registering") and trips the duplicate guard
 * when it executes a second time. Deriving it removes the chance of drift.
 */
function packageName() {
  const manifest = JSON.parse(readFileSync(join(ROOT, 'package.json'), 'utf8'))
  if (typeof manifest.name !== 'string' || manifest.name === '') throw new Error('package.json has no name')
  return manifest.name
}
```

然后把 `buildBundle()` 里所有 `${PACKAGE_ID}` 换成 `${id}`（`id = packageName()`，函数开头取一次）：

```js
export function buildBundle() {
  const id = packageName()
  ...
  window.__ModuleLoader__.load({
    id: '${id}',
    ...
    exports.name = '${id}'
```

**`tools/client-selftest.mjs:112`** —— 断言改为跟着包名走：

```js
assert(entry.id === pkgName, `wrong id: ${entry.id}`)   // pkgName = 该测试里已读到的 package.json name
```

**`tools/impl-selftest.mjs:1392`** —— 这条**保持不变**（它守的是插件身份，不是模块 id）：

```js
assert(inserted.id === 'dsh-novel', 'the plugin id stays dsh-novel — it is the route prefix and the skill namespace')
```

### 3.2 明确"不要动"的清单（都是对外契约）

| 项目 | 值 | 为什么不动 |
|---|---|---|
| patch 的 `insert[0].id` | `dsh-novel` | 插件 id，服务/路由的身份 |
| `lib/index.js:25` `export const name` | `'dsh-novel'` | 同上 |
| 路由前缀 `lib/impl/router.js:26` | `/dsh-novel` | 已写进文档与自测（`api-selftest.mjs`、`INSTALL.md` 的 health 命令） |
| 写头 `x-dsh-novel` | 不变 | 客户端与宿主成对使用 |
| localStorage 键 | `dsh-novel.*` | 改了会丢用户已选的项目根 |
| 技能命名空间 / 面板 id | `dsh-novel.*` | 技能目录与面板键 |

只有**客户端模块 id** 这一项从 `dsh-novel` 变成 `dsh-novelsupport`（跟随包名）。

### 3.3 安装方式：只保留一种，并绕开 npm 上的同名包

现在 profile 里**已经没有 novel 这一行**了（20:48 插件管理器重写 patch 时把它连同 `agent-default-model` 一起去掉了），`/dsh-novel/health` 目前 404。重装时按下面来：

**方案 A（推荐，已实证可用）—— patch 里按包名 insert，包里用 tarball 装到位**

1. profile 的 `package.json` **不要**把 novel 写进 `dependencies`，也**不要**写进 `dsh.profile.bundles`（任何一次 pnpm install 都会去 npm 解析同名包）。
2. 按 `INSTALL.md` 把 `dsh-novelsupport-0.0.1.tgz` 解到 `profiles\desktop\node_modules\`，目录名用**包名**：

   ```powershell
   tar -xzf dsh-novelsupport-0.0.1.tgz -C D:\dsh-home\profiles\desktop\node_modules
   Rename-Item D:\dsh-home\profiles\desktop\node_modules\package D:\dsh-home\profiles\desktop\node_modules\dsh-novelsupport
   ```

   > 注意 `INSTALL.md` 现在还写着 `Rename-Item ... node_modules\dsh-novel`，这是改名前的残留，它和 `cordis.patch.yml` 里的 `name: 'dsh-novelsupport'` **互相矛盾** —— 照它做出来的目录名宿主解析不到。请把 INSTALL.md 一起改成 `dsh-novelsupport`（`tools/package-plugin.mjs:226-259` 里生成这段的模板也要改）。
3. patch 里保留一行，name 用**包名**：

   ```yaml
   - insert:
       - id: dsh-novel
         name: 'dsh-novelsupport'
   ```

**方案 B（开发期最省事）—— 绝对路径 insert**

```yaml
- insert:
    - id: dsh-novel
      name: 'D:/documents/GitHub/my-project/lib/index.js'
```

这条路径走 `isAbsolute()` 分支，**完全不查 node_modules**（`dsh-client-modules/lib/index.js:745-752` 注释里你们自己已经记过），因此不会再碰到 npm 上的 `dsh-novel@0.1.1`。代价：客户端仍然按"从该文件向上找到的 package.json 的 name"取名（`nearestPackage`，第 774-790 行），所以**仍然要求 3.1 那处修改**——id 还是得等于包名。

**两种方式只能存在一种。** 同时留着"绝对路径行"和"包名行"，宿主会抛 `package dsh-novelsupport resolves from multiple active Loader sources: ... remove one entry`（`lib/index.js:876`）——那是另一种报错，别把它误判成本次故障。

### 3.4 顺手排掉地雷：npm 上的 `dsh-novel@0.1.1`

`D:\documents\GitHub\my-project` 的包名已是 `dsh-novelsupport`，与 npm 上那个 `dsh-novel@0.1.1`（它把 8 个 `@deepseek-ai/dsh-*@0.1.0-rc.6` 当**普通依赖**）不再是同一个名字。这是好事，但要注意：

- 只要 patch 里出现 **`dsh-novel`** 这个名字（而不是 `dsh-novelsupport`），宿主就会去 npm 解析，18:54 那次的根因会原样回来。
- 所以：**永远不要**在 patch / `dependencies` / `bundles` 里写裸名 `dsh-novel`。

## 五、这次为什么值得单独记一笔

前一次故障（18:54–19:21）是**依赖树**问题：包被提升、旧核心包遮蔽运行时 → 表现为 host 侧 `disabling profile plugin row` + 必需插件不激活。

这一次是**模块身份**问题：包名、插件 id、客户端 bundle 注册 id 三个概念被当成了一个 → 表现为渲染侧 `duplicate factory registration` + 一行 `import failed`。

两者的共同教训是：**DSH 的插件有三重身份，不能混用**——

| 身份 | 取值来源 | 谁在用 |
|---|---|---|
| 包名 | `package.json.name` | npm 安装、宿主模块解析、**客户端图的键** |
| 插件 id | patch `insert[0].id` | 服务名、路由/日志前缀、技能命名空间 |
| 客户端模块 id | bundle 里 `__ModuleLoader__.load({id})` | **必须等于包名** |

前两者可以不同（你们这次的改名正是如此，且是对的），第三者**必须等于包名**。
