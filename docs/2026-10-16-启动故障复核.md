## 二、需要修正的部分

### 1. 根因归属不准：引入旧核心包的不是"4 个第三方插件"，而是 npm 版 `dsh-novel@0.1.1`

报告 §二.2 说 4 个插件依赖 `@deepseek-ai/dsh-*@^0.1.0-rc.x`。实测：

| 包 | 与 dsh 相关的依赖声明 | 是否会拉入旧核心 |
|---|---|---|
| dsh-cost-meter 1.8.32 | `peerDependencies`: dsh-credentials / dsh-home-paths（范围含 `>=0.2.0-rc.1`）；**旧版只在 devDependencies** | ❌（devDeps 不安装） |
| dsh-token-skills 0.1.0 | 仅 peer `@deepseek-ai/cordis`（被兼容性检查忽略） | ❌ |
| dshmarket 1.66.28 | peer `@deepseek-ai/dsh-settings`（范围含 `^0.2.0-rc.1`）；旧版只在 devDependencies | ❌ |
| **dsh-novel 0.1.1（来自 npm）** | **`dependencies` 硬钉**：`dsh-client-runtime/dsh-client-ui-conversation/dsh-client-ui-primitives/dsh-host-webserver/dsh-session/dsh-skill/dsh-system-prompt/dsh-tools` = **0.1.0-rc.6** | ✅ **就是元凶** |

关键点：profile 的 `dependencies` 写的是 `"dsh-novel": "^0.1.1"`，而本地 junction 仓库 `D:\documents\GitHub\my-project` 的 `dsh-novel` 版本是 **0.0.1**（不满足 `^0.1.1`）。所以 pnpm 实际装的是 **npm 上的 `dsh-novel@0.1.1`**，它把 0.1.0-rc.6 的八个核心包作为**普通依赖**装进了 profile 顶层（备份里还能看到 `dsh-novel-npm-0.1.1\` 目录），并由这八个包继续带入 rc.8 的传递依赖。

→ 因此报告 §五.2「需要先把 `D:\documents\GitHub\my-project` 的依赖升级到 0.2.0-rc.2」**指错了对象**；真正要处理的是 npm 上的 `dsh-novel@0.1.1`（或在 profile 里用 `link:`/`file:` 显式指向本地 0.0.1 仓库并自行对齐 peer 范围）。

报告 §四 的验证是在「`cordis.patch.yml` 已被清空（217 字节）」的配置下完成的。但现场现在：

当前进程 19:40 启得起来，只说明**空 patch** 的修复态可用；**当前这份 patch 尚未经过一次干净的冷启动验证**（除非 19:42 那次是热重载）。若下次冷启动失败，第一嫌疑就是这份 patch，而不是 node_modules。

### 3. 三处细节与现场不符

2. 报告说移出 `pnpm-lock.yaml`，实际备份里同时存在 `pnpm-lock.yaml` 与 `pnpm-lock.yaml.moved`，且两者哈希相同 —— 真实动作是「先重命名为 `.moved`，再补了一份副本」，属无损，但描述不精确。
3. 报告 §五.2 把 `dsh-novel` 描述为「通过 junction 指向本地仓库」属实，但没说明**实际生效的不是这个 junction**（见 §二.1）——这一点恰恰是根因所在。

## 三、报告未覆盖、但值得盯的风险

1. **第三方插件其实早已全部停用，却仍留着依赖声明** —— `package.json.bak-before-repo-restore-20261016-183115`（18:31 的快照）显示当时 `bundles` 里还有 `dsh-cost-meter`、`dsh-token-skills`、`dsh-novel`、`dshmarket`；到 19:20 的备份时已只剩默认两项。也就是说 19:20 之前它们已从启用列表移除，只是依赖还挂在 `node_modules` 里继续作祟。报告的叙述顺序（先移除 node_modules、再清 dependencies）掩盖了这一关键时间线。
2. **"只移出不删除"的代价**：`pnpm-workspace.yaml` 仍保留 `nodeLinker: hoisted`、`autoInstallPeers: false`，以及为 `dsh-cost-meter@1.8.30 || 1.8.32`、`dshmarket@1.66.28` 写的 `minimumReleaseAgeExclude` 规则。下次插件管理器只要再执行一次安装，hoisted 策略会**原样重演**本次故障（所以报告 §五.1 的告诫是对的，但应升级为「清理 profile 层的安装配置」）。
3. **`web` profile 是同类隐患**：`D:\dsh-home\profiles\web` 仍有 `node_modules` 与 `pnpm-lock.yaml`，且 `dependencies` 里钉着 `@deepseek-ai/dsh-client-ui-primitives@0.1.5-rc.1`（自带运行时该包为 0.2.0-rc.2）。它只声明 peer `@deepseek-ai/cordis`（被兼容性检查忽略），所以暂时不会被判为不兼容；但一旦以 `web` profile 启动、或该包被提升为 bundle 行，就可能复现同类问题。
4. **`@deepseek-ai/dsh-settings` 这颗雷**：`dshmarket` 的 peer 范围同时接受 `^0.1.0-rc.7` 与 `^0.2.0-rc.1`，两个大版本都能通过校验 —— 说明这套兼容性门槛能挡住明显错版，但挡不住语义漂移。报告 §五.1 的「先确认兼容 0.2.0-rc.2」建议应当按此收窄为「不要相信 peer 范围，按实际行为回归」。
5. **附带安全项**：报告附录列出的三个中间产物（`dsh_boot_before.log` 等）里含有启动输出，而 Web 启动行形如 `dsh web: http://127.0.0.1:19387/?token=xxxxx`。请确认这三个文件里是占位符而非真实 token；若是真 token，建议清掉。
